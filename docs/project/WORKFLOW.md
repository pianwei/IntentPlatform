# 从需求到交付的工作规则

适用于本项目已授权的规划、实现、验证与交付；全局固定约束见 [AGENTS.md](../../AGENTS.md)。

## 按影响选择流程

| 等级 | 典型触发 | 最小过程 | 必需记录与验证 |
|---|---|---|---|
| A | 文案、文档、无行为影响的局部样式 | 定位 → 修改 → 相关检查 → 交付 | 已有任务或交付说明；内容、链接或受影响页面检查，不机械新增测试 |
| B | 独立功能或局部缺陷 | 验收条件 → 简短方案 → 实现 → 定向验证 → 交付 | 一条任务；正常、异常、边界及适用回归用例 |
| C | 共享契约、权限、状态机、迁移、重要依赖、跨模块行为 | 影响分析 → 契约和方案 → 拆分 → 集成验证 → 审查 | 受影响调用方、兼容性与专项证据；实质取舍才写决策 |
| D | 用户指定大版本、系统性调整、广泛不兼容变更 | 版本范围 → 阶段交付 → 候选版本 → 全量验证 → 发布/移交 | 完整软件套件、完整 Agent 评测及适用的升级恢复；不能以局部通过替代 |

影响扩大时升级范围并记录理由，不为省事降低已确定的验证要求。专项规则见 [TESTING.md](TESTING.md)；新增第 21 项、全局模型或提示变化即使表面很小，也有更广的回归要求。

## 需求与变更

先把用户目标映射到 REQ 编号，明确可观察结果、输入输出、关键异常与本次范围外事项。局部变化可写在任务内，不强制独立 PRD。业务目标不明时查已有资料；不能从资料确定且会改变结果的决策写入 DECISIONS.md 并集中询问，同时继续不依赖它的工作。

范围变化记录“来源、原行为、新行为、影响任务/接口/评测/里程碑、决策依据”。优先采用最新用户要求和已确认当前基线，保留旧方案未冲突目标。新增独立产品模块、扩大范围或改变已确认交互先供用户审核；已授权范围内常规实现不重复审批。重大取舍写 DECISIONS，普通实现无需 ADR。

## 任务就绪与状态

[TASKS.md](TASKS.md) 是唯一任务状态源。每个开发任务至少包括：ID、目标、关联需求、范围、可观察验收、负责人、等级、依赖/阻塞、验证计划与结果、目标版本（可为未指定）、下一步。只有目标明确、关键决策可用、验收可执行且已有承担人，才转为“可开发”。规划任务使用“可执行”作为同等状态。

建议状态：待梳理 → 可执行/可开发 → 进行中 → 待验证/审查 → 已交付。需要远程集成和发布时，进一步使用“已合并待发布”“已发布/已验收”；阻塞单独记录原因、解除条件和受影响范围，不覆盖已有进展。

每条任务保留四个独立事实字段：**实现或产出、验证、集成、交付**。编写完成不意味着验证通过；本地交付不意味着 Git 合并或生产上线。完成条件由用户委托范围决定；只要求本地代码时不强制等待生产，要求上线时继续完成已授权的部署与上线验证。缺必需验证则保持待验证，不能写“已交付且通过验收”。

初始任务可在未分配负责人时排入待梳理；启动执行前根据实际承担者补齐。未指定负责人和日期不等于已形成可执行承诺。

## 协作、进度与恢复

每个任务一个协调者负责 TASKS.md、共享契约、依赖锁及版本元数据的最终归并。能独立验证且有文件边界的工作才并行；子执行者写各自成果并返回证据，不同时编辑状态源。集成后按组合影响验证，不把各自通过相加当作集成通过。

工作暂停或交接前写明产出位置、当前文件/提交状态、最近有效证据、未决问题和下一步。新会话先核对实际文件、分支和证据再继续，不能依据旧摘要直接声称已完成。用户询问进度时报告真实结果，保留仍有效的任务目标。

阶段退出条件是结果检查，不自动变成人工审批。真实业务取舍、已有项目审查要求与权限边界仍须满足；已有明确授权无需重复确认。

## 代码、Git 与检查自动化

复用已有工程结构、依赖和脚本。读取相关代码及调用方再改动；保留与本次无关的修改。当前无代码/Git/CI 时不虚构命令、提交或成功结果。

建立 Git 策略时默认建议受保护主分支与短期任务分支；分支名关联真实任务，如 `feat/INT-005-vertical-flow`。实际主分支名、远程和保护规则须按环境落实。提交可采用约定式类型，说明具体变化；破坏兼容标明影响。

PR 说明最终问题、行为、关联任务、验证与适用迁移风险。发布权限不由“开发”自动推导。CI 必需项、审查责任和分支保护须在代码托管平台实际配置后才标为生效；仅写入本文不能充当强制门禁。工程建立后将已验证的测试命令接入 CI，运行成功且未被跳过才算通过。

## 验证与交付证据

按 TESTING.md 执行与风险匹配的检查。基线失败、本次新增失败、未执行及不适用分别记录；不以降低断言或更改验收口径消除失败。配置/代码再次改变后补跑失效证据涉及的检查，稳定通过后不无故重跑全量。

测试结束无论成功或失败，先保存报告与必要排错日志，再按 [测试环境清理](TESTING.md#测试环境清理) 立即删除本轮独立测试容器、网络和卷，核对清理结果；仅停止不算完成。已有授权覆盖这项收尾，不重复询问。只有用户明确要求保留现场才例外；归属不明或共享资源不删除，清理失败记录原因和残留，自动化入口返回非零，不能写成已清理。

小任务证据可直接写入 TASKS.md；复杂任务在 `records/任务ID-主题.md` 记录，避免复制报告。每包结束检查目标/范围、接口/使用说明、验证证据、Skills影响；TASKS四项事实中记录更新项或无需修改原因。Skills仅维护稳定方法与入口，历史证据保留，当前事实入口要一致。结束时说明结果、证据、交付位置、尚未满足条件。

## 版本、移交与反馈

方案版本、软件版本、FunctionVersion、AgentRelease 分别管理。软件版本从届时真实工程配置的单一来源读取；产品的发布快照关联代码/构建、功能版本、本体投影、模型标识与参数、提示策略、组件、评测集及评分口径。无正式发版任务时不递增版本或创建 Tag。

发布前形成版本范围、候选物、验证、兼容/迁移、目标环境、恢复触发条件和操作顺序。数据恢复与代码回退分别评估；Agent 行为恢复需匹配模型、提示、功能和权限配置。权限撤销不得因回滚失效。只在既有授权内执行远程、生产或有副作用的操作；缺少必需授权时，先完成可审查的准备工作并准确记录待授权状态。

交付后收到真实反馈，关联原版本、REQ、复现材料和影响，形成新任务或重开原任务；每次有实际迭代结果再复盘返工、交付周期、缺陷及相关质量/延迟。重复问题才沉淀新规则，过期规则及时简化。没有监控或调度时不声称会在离线后持续巡检。
