# INT-011 finite source / OpenAPI / HTTP-v2 contract

Additive backend contract; old document text, immutable releases, HTTP connector `1`, and router/compiler versions stay intact. New schema migration is `0004`. All management routes below require an active workspace maintainer; runtime tokens cannot use them. No input can expand server target or credential grants.

## Versioned documents

Prefix `/api/v2/management/workspaces/{ws}`.

- Existing `POST /documents` multipart `file` remains compatible, now stores original bytes and immutable revision 1. Supported readable TXT/MD/DOCX/PDF plus UTF-8 JSON/YAML sources. Response adds `revision`, `original_available`, `sections:[{id,heading,start_line,end_line,text}]` to existing id/filename/text/source.
- `GET /documents` lists `{id,filename,latest_revision}`. `GET /documents/{id}/versions` and `GET /documents/{id}/versions/{revision}` expose immutable text/sections and original availability.
- `POST /documents/{id}/versions` multipart `file,expected_revision` creates the next version, stale 409. Stable section IDs are retained by unique heading/paragraph identity where possible; citations always bind document ID + revision + section ID + exact excerpt.
- `GET /documents/{id}/versions/{revision}/original` downloads the actual stored original. Legacy documents are migrated as text-only revision 1 (`original_available:false`); no original binary is fabricated.

Every full document response is `{id,filename,revision,text,sections,original_available,source:{document_id,revision},fixture_mode:false}`; `id` is the stable document ID, never the internal version-row ID. Malformed new revision uploads return 422 without consuming a revision. Long source lines are split into exact bounded excerpts; original text and bytes remain intact. New domain-source references can select these exact versions and section IDs (a unique heading is also accepted); old immutable domain definitions are not rewritten.

## OpenAPI import

- `POST /openapi-imports` body `{document_id,revision}` parses that immutable source; response `{id,document_id,document_revision,parser_version,valid,diagnostics,operations}`.
- `GET /openapi-imports/{id}` returns the retained parse result. Each operation is `{key,method,path,operation_id,summary,source_pointer,supported,diagnostics,definition,facts}`. Key is `METHOD /path`, definition is a proposed functional draft, never published. Diagnostics have `{code,message,pointer,severity:"error"|"review"}`. `definition` is null for unsupported operations; operation_id may be null.
- `POST /openapi-imports/{id}/functions` body `{operation_key,name?,description?}` selects a supported operation and creates a normal FunctionOut with source review required. Import selection neither calls the endpoint nor grants permissions.

Finite parser: OpenAPI 3.0.x JSON/YAML, a single uploaded document, internal JSON Pointer `$ref` only. Remote/file-relative refs, cycles, YAML aliases/custom tags/duplicate keys, JSON duplicate keys, excessive nesting/expansion/operation counts, unresolved refs and unsupported structural schemas are rejected. Supported operations are GET/POST; scalar path/query/header parameters and flat JSON object request bodies map explicitly. Cookie parameters, complex style/explode encodings, callbacks, multi-server variables, polymorphic schemas and unsupported request media produce diagnostics and cannot be selected. Security requirements are shown as review requirements, never converted to a key or a grant. Reference locations retain original pointers.

Limits: extracted source 500,000 characters, 512 sections, input nesting 32 and 25,000 nodes; expanded references 40 levels, 40,000 nodes and 2,000,000 cumulative UTF-8 text/key bytes; at most 100 operations and 4,000,000 serialized operation-report bytes. Repeated reference text counts each expansion. Overflow returns a diagnostic with no selectable operations.

## HTTP connector version 2

`connector:{kind:"http",version:"2",endpoint,method,credential_ref?,...existing response/status settings,http_mapping:{path:{wire_name:argument_name},query:{wire_name:argument_name},headers:{wire_name:argument_name},body:{wire_name:argument_name}}}`.

The scalar parameter argument names generated by imports include their location (for example `path_item`, `query_item`) so colliding wire names do not overwrite each other. `body` maps explicit top-level JSON fields from flat input arguments; scalar and scalar-array body fields are supported, nested objects are rejected in this finite version. Query and JSON body are transmitted together without loss. Every defined input must have one explicit destination; duplicate destinations/arguments, missing path placeholders, unsupported arrays in scalar slots and GET bodies are rejected. Headers such as Authorization, Proxy-Authorization, Host, Cookie, forwarding, content framing, Origin and reserved idempotency headers cannot be supplied by mapped arguments. Credentials and idempotency headers are applied by the server only.

Path values are encoded as one segment; empty/dot/traversal/slash/control encodings are rejected. Both template and fully substituted URL must remain within workspace target grants. Credentials bind the original endpoint template and optional status template; final origin/path authorization is checked again before transmission. Object authorization and the final Worker dispatch callback still gate the actual request. HTTP v1 stays on its original implementation.

`http_body_required:boolean` defaults false. Imported required JSON bodies set it true, so an empty required schema sends `{}`; an operation with no body sends none. GET bodies are rejected. `http_failure_statuses:Array<400|404|409|422>` defaults empty and requires explicit business review. An exact configured status plus a JSON object response establishes a definite business failure; unconfigured 4xx, 401/403, 5xx, timeouts, connection failures and malformed responses do not. Status-query errors are never treated as business-terminal failure by this mapping. Both HTTP versions reject configured credential/idempotency headers that override Host, framing or proxy routing; the transport checks them again.

## Source review and publication

- `PUT /functions/{fid}/sources` body `{revision,citations:[{field_path,document_id,revision,section_id,quote,proposed_value}]}` records reviewed source claims, increments the function revision and invalidates validation/confirmations. `quote` must occur in the named immutable section. Claims are attributed to the acting maintainer, not asserted as automatic extraction truth.
- `GET /functions/{fid}/source-review` returns `{revision,required,ready,issues:[{field_path,kind,current_value,candidates,resolved,reason}],api_source,api_facts,citations}`. The complete source lists are returned even when there are no issues; clients must not reconstruct citations from issues. `PUT /sources` and POST confirmation return this same shape. API candidates are `{kind:"api",value,source_pointer,ref_targets}`; document candidates are `{kind:"document",value,document_id,revision,section_id,quote,claimed_by}`. Stored citations add `claimed_by`; omit that server field when saving. `api_source` contains document_id/revision/import_id/operation_key/pointer/parser_version. Imported API facts and cited document claims remain separately labelled. Divergence from a source fact is a conflict. Business interpretation/effect/success/output and HTTP failure mappings of an imported operation always require human review, even if there is no textual conflict.
- `POST /functions/{fid}/source-review/confirm` body `{revision,resolutions:[{field_path,reason}]}` confirms the already edited current value with a nonempty reason. It does not silently edit the definition. The confirmation binds exact revision/value/source claims; any draft/source change invalidates it.
- Existing validate/publish routes apply these gates when source review is required. Unresolved conflicts/reviews, unavailable source revisions, invalid HTTP mappings or failed probes prevent publication. Function versions and AgentRelease source manifests pin immutable document revisions and reviewed excerpts. Old no-source-review function versions keep legacy compatibility.

Validate accepts `{revision?,arguments,probe,allow_effects:false,failure_arguments?:object}`. Current frontend always supplies revision; mismatch is 409. OpenAPI-selected functions require a real successful probe followed by a definite failed probe using schema-valid failure_arguments on this revision. WRITE requires explicit allow_effects for both calls in an authorized test environment. `checks.failure_probe` is `{status,expected_status:"FAILED",http_status_code:number|null}`. A failed successful-probe attempt does not launch the failure probe. Publish accepts `{revision?}`, also stale 409; legacy omitted revisions remain supported but the locked current draft must have matching successful validation and source confirmations.

The parser proposes API facts and leaves business semantics for explicit correction/confirmation. It does not infer private API guarantees from prose, execute imported code, fetch external refs, or claim real bank acceptance. Official basis: [OpenAPI 3.0.3 parameter objects](https://spec.openapis.org/oas/v3.0.3#parameter-object) and [reference resolution](https://learn.openapis.org/referencing/resolve.html).
