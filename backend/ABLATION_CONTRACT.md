# INT-012.3 finite model projection and shadow comparison

This package introduces `router-v3` without changing the implemented `router-v1` or `router-v2` prompts and payloads. New publications containing finite-json-v2 capabilities select v3; old immutable releases and conversations retain their existing router. The compiler stays finite-json-v2. No database migration is required.

## Normal v3 routing

The actual model request includes every currently authorized capability card and one deterministic, deduplicated domain projection containing pinned versions/source definitions, concepts, inheritance closure, relations, units and conversions. Conflicting same-ID/version projections fail closed; no top-K candidate filter or silent truncation is used. Candidate-to-domain version references remain explicit. Only authorized candidates contribute projections. Trusted result context follows the existing bounded context policy. Secrets, connector endpoints and credentials are never model-card fields.

V3 uses the existing explicit semantic proposal schema and the same deterministic entity/history/semantic/parameter/precondition gates before ordinary dispatch. V1/v2 still use their original payloads, parser and profiles. Fixture mode is identified as a deterministic tool test and does not claim a real model request.

## Controlled shadow API

`POST /api/v2/runtime/conversations/{cid}/shadow-comparison` accepts exactly `{release_id,text}`. No gold labels, expected outputs, alternate model settings, candidate list, supplied context or arbitrary policy is accepted. `text` is bounded to 8,000 characters. It requires the actual conversation's scoped runtime owner, an effective workspace publisher/admin role, and server setting `INTENT_ALLOW_SHADOW_EVALUATION=true` (default false). Ordinary chat has no ablation switch. A workspace permits at most one simultaneous shadow comparison, with three finite model attempts.

All three arms share the same pinned release, actual authorized candidate set, model profile, input text, server reference time and authorized history snapshot. Each arm receives an independent model invocation. Authorization is checked again between invocations and before returning evidence. Changing authorization/configuration fails closed; no old evidence is returned after revocation. No business connector is invoked; no Run, Call, Event, confirmation or conversational state is created/changed. Read-only trusted resolvers may be queried during context/binding checks under the existing finite budget.

- **A `description-parameters-v1`**: capability IDs, names/descriptions and parameter schemas only. Base routing/parameter validation is retained; ontology semantics are absent. Missing trusted entity information remains a clarification or explicit unknown, never a model-supplied business ID accepted as trusted.
- **B `domain-semantic-v1`**: the complete v3 payload and deterministic semantic checks, including relations, followed by the existing trusted binding/normalization/precondition gates.
- **C `without-relations-v1`**: same as B except structured registered relations (including nested package definitions) and capability relation assertions are removed from both actual model input and relation checks. Inheritance, object/action/result, participant cardinality, units/dates and trust checks remain. Unstructured source descriptions are retained; no claim is made to erase natural-language relational hints. This removes structured relation information/checks jointly; it is not an isolated prompt-only experiment.

Result envelope: `{schema_version:"1",kind:"intent-shadow-comparison",acceptance_evidence:false,release_id,conversation_id,reference_time,profile,candidate_ids,context,context_stats,variants:[{variant,policy_version,outcome,decision,proposal,validated_requests,question,validation,model_request,model_response,model_ms,validation_ms,faults,fixture_mode}],business_execution:{status:"NOT_EXECUTED",count:0}}`. Unknown/skipped timings are null. Model request means the actual JSON request body, without transport headers/URL; response means the actual returned JSON, or null on transport failure. Error/timeout/malformed responses remain arm failures. Fixture observations carry null wire request/response and explicit fixture mode. Model requests never receive gold data.

The shadow result predicts a route/clarification only; `NEEDS_CONFIRMATION` is an unaccepted requirement and cannot authorize an execution. It does not replace normal B end-to-end or S3 conversational evaluation. Human labels, real resources, production performance and statistical significance remain separately verified.

The complete actual model body is bounded to 2,000,000 UTF-8 bytes and is rejected rather than silently truncated. Context/binding authorization has an overall finite resolver budget plus 40-call/20-second phase budgets. Changed conversation sequence, authorized candidates, configuration, history or entity authorization refuses the comparison. The shared history snapshot is explicit; external resolver data is live and cannot be claimed to be a frozen bank dataset. A missing bound entity produces clarification, and unknown trusted facts never become true.

## Finite CLI evidence

`python scripts/evaluate_shadow.py --dataset dataset.json --bindings bindings.json --base-url URL --trial-id ID --output DIRECTORY` accepts a dedicated shadow dataset of 1–200 cases with `{dataset_id,version,purpose:"development"|"sealed",review_ref?,frozen_ref?,cases:[{case_id,conversation_id,release_id,text,expected:{decision,capability_ids}}]}` and bindings `{bindings:[{conversation_id,env_var}]}`. Tokens are read only from named environment variables. Sealed execution requires review_ref and frozen_ref plus the independent `--allow-sealed` switch.

The CLI sends only each case's text/release ID to the controlled API. It retains every case and every A/B/C arm, including missing/failed/timeout evidence, in denominators. Comparison scores are exact decision and complete capability-set agreement; these limited shadow metrics are separate from gold-exact-v1 E2E reports. Raw evidence remains available for independent analysis. No comparison is labelled causal or statistically significant.

Capability sets use unique sorted stable IDs. Repeated independent requests for one capability do not create duplicate set members; their arguments/counts remain in raw evidence and are outside this limited metric. Function ambiguity compares the authorized function-choice option IDs. Entity/history ambiguity compares the proposed selected capability IDs, never opaque entity/history choice IDs. Gold capability sets reject duplicates. A routable response without a selected capability, or an ambiguity response with missing/unknown candidate information, becomes an observation error instead of matching an empty gold set.

Reserve a new safe trial directory before requests; never overwrite or retry a submitted comparison after an uncertain timeout. Archive `shadow.json` using an exclusive atomic commit. Dataset/report values remain exact; known-secret contamination refuses the archive. Wire evidence uses controlled redaction and explicitly records any change. Unknown business secrets require caller review. The CLI does not claim acceptance or produce a valid archive from partial serialization.

## File and validation boundaries

New modules are `routing_v3.py`, `shadow_evaluation.py`, `shadow_api.py` and `shadow_cli.py`; a thin `scripts/evaluate_shadow.py` invokes the CLI. Narrow existing edits register v3, select it for new domain releases, enable the controlled setting/router and teach Worker the new semantic parser/context path. New tests cover actual model socket payloads, authorized full projection, relation removal, failure denominators, zero dispatch, release compatibility, revocation and archive integrity. Existing evaluator scoring semantics are unchanged. The separately owned process-fault harness files are untouched.
